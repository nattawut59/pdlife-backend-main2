# PDLIFE Backend — API Contract

Complete endpoint reference for building a separate frontend (mobile app and/or web
dashboard) against this backend. This is the ground-truth contract — every field name,
type, and validation rule here is copied directly from `src/schemas/*.ts` (Zod, request
validation) and `src/types/database.ts` (response shapes). If frontend code disagrees with
this file, this file is right — it's generated by reading the same source the backend runs.

For narrative walkthroughs of common flows (login → onboard → prescribe → answer a round →
dashboard), see `API_EXAMPLES.md` instead — this file is the exhaustive reference.

## Base setup

- Base URL: `<BACKEND_URL>/api` (dev: `http://localhost:3000/api`)
- Auth: `Authorization: Bearer <token>` header on every endpoint except `/auth/register` and `/auth/login`
- Content-Type: `application/json` on every request with a body
- Error shape (any non-2xx):
  ```json
  { "error": "string", "details": { "fieldName": ["validation message"] } }
  ```
  `details` is only present for 400 Zod validation failures.

## Roles

`patient | caregiver | nurse | doctor | admin`. Public self-registration only allows
`patient`/`caregiver` — staff accounts come from `/auth/provision` (admin-only).

## Auth

### `POST /auth/register` — public
```ts
// request
{
  first_name: string;
  last_name: string;
  user_name?: string;      // 3-50 chars, defaults to phone_number if omitted
  password: string;        // min 8 chars
  role: "patient" | "caregiver";
  phone_number: string;    // Thai format, e.g. 0812345678 or +66812345678
  preferred_language?: "th" | "en";

  // role: "caregiver" only — required, rejected with 400 if missing
  prefix?: string;             // คำนำหน้า เช่น นาย/นาง/นางสาว
  gender?: "male" | "female" | "other";
  date_of_birth?: string;      // YYYY-MM-DD
  relationship?: string;       // ความสัมพันธ์ทั่วไป — ค่าเริ่มต้น ไม่ใช่ตัวเดียวกับ
                                // patient_caregivers.relationship ที่กรอกตอนผูกกับผู้ป่วยแต่ละคน
  address_line?: string;
  subdistrict?: string;
  district?: string;
  province?: string;
  postal_code?: string;        // 5 digits
}
// 201 response
{ user: SafeUser }
```

### `POST /auth/provision` — admin only
Same body as register, but `role` accepts any of the 5 roles.

### `POST /auth/login` — ⚠️ legacy, staff-with-no-email only
```ts
// request
{ user_name: string; password: string; }
// 200 response
{ token: string; user: SafeUser }
```

**Mobile apps must not use this.** It verifies `users.password_hash`, and accounts created by
`POST /auth/register` don't have one — self-signup creates the credential in Supabase Auth and
leaves `password_hash` NULL on purpose. So a patient who registers through the app and then calls
this endpoint gets `401 Invalid username or password` every time, forever, with nothing in the
data to explain why.

The only accounts that can still log in here are staff provisioned through `POST /auth/provision`
*without* an email (the legacy branch). This route disappears in phase 3 along with `password.ts`
and `signToken`.

Patients and caregivers authenticate against **Supabase Auth directly** with phone + password and
send that `access_token` as the bearer — see `docs/MOBILE_INTEGRATION.md` §1–2 for the client
setup. `POST /auth/register` still creates the account; only the *login* step moves to Supabase.

### `GET /auth/me` — any authenticated user
```ts
// 200 response
{ user: SafeUser }
```

`SafeUser` = the `users` row minus `password_hash`:

```ts
  phone_number: string | null;
  preferred_language: "th" | "en";
  last_login_at: string | null;   // ISO datetime
  is_active: boolean;
  deactivated_at: string | null;

```

## Patients

Access rule used throughout this section (`assertCanAccessPatient`): the patient themself,
any of their **active** linked caregivers, or any staff (nurse/doctor/admin). Write actions
that count as "answering on the patient's behalf" additionally require the caregiver link's
`can_answer = true`.

## Appointments

No doctor-schedule table exists anywhere in the schema — every doctor is treated as bookable
every day the clinic is open, `08:00`–`17:00`, fixed 30-minute slots
(`APPOINTMENT_SLOT_MINUTES`/`CLINIC_OPEN_TIME`/`CLINIC_CLOSE_TIME` in `config/constants.ts`).
One doctor can hold at most one appointment per slot, enforced two ways: a pre-check
(`findByDoctorAndSlot`) for a friendly 409, and a partial unique index
(`migrations/0005_one_appointment_per_doctor_slot.sql`) as the real guarantee under concurrent
requests.

### `GET /appointments` — role: nurse/doctor/admin
Three views through one endpoint since they return the same shape: `?date=` (default today,
Thai calendar) for the daily schedule, `?before=` for the "past visits" list, `?patient_id=` for
one patient's full history. Don't combine query params — nothing consumes a combination today.
```ts
{
  date: string | null;   // null unless ?date= (or the default) was used
  appointments: Array<{
    id: string; patient_id: string; patient_name: string | null; hn_number: string | null;
    age: number | null; visit_date: string; visit_time: string | null;
    visit_type: "routine" | "follow_up" | "urgent" | "walk_in";
    status: "scheduled" | "checked_in" | "completed" | "missed" | "cancelled";
    doctor_name: string | null;
    screening: { status: "draft" | "submitted" | "doctor_opened"; screened_by: string | null; submitted_at: string | null } | null;
    doctor_note_at: string | null;
  }>;
}
```

### `GET /appointments/counts?from=&to=` — role: nurse/doctor/admin
How many appointments fall on each day in a range — enough to draw dots on a week strip or an
"upcoming days" card without pulling the appointments themselves.
```
?from=YYYY-MM-DD   both required
?to=YYYY-MM-DD     range must be under 31 days, and `from` must not be after `to`
```
```ts
{ from: string; to: string; counts: Array<{ date: string; total: number }> }
```
`counts` is **sparse** — days with no appointments are omitted rather than returned as `0`, since
the caller already knows which dates it asked about. Status is not filtered, matching
`GET /appointments?date=`, so the number here always equals the number of rows you get when you
open that day. Staff-only even though it returns nothing but integers: how busy the clinic is on a
given day isn't something a patient should be able to read off.

### `GET /appointments/available-slots?doctor_id=&date=` — any authenticated
Full slot grid for one doctor on one day, not just the free ones — lets a picker render every
slot and grey out the taken ones. Both params required. No role gate: this isn't patient data,
and the patient app needs it too before self-booking.
```ts
{ doctor_id: string; date: string; slots: Array<{ time: string; available: boolean }> }
```

### `POST /appointments` — role: nurse/doctor/admin
Staff-side booking, covers both scheduled visits and walk-ins. `doctor_id`/`visit_time` can be
left unset (doctor not assigned yet); slot-boundary validation only kicks in once both are
present. Past dates are allowed on purpose — catching up on data entry is normal, the screen is
what should warn about a stale date, not the API.
```ts
// request
{
  patient_id: string; doctor_id?: string | null;
  visit_date: string; visit_time?: string | null;   // "HH:MM"
  visit_type: "routine" | "follow_up" | "urgent" | "walk_in";
  status?: "scheduled" | "checked_in";   // default "scheduled"
}
// 201 response
{ appointment: <same shape as GET /appointments row above> }
```
409 if the patient already has an appointment in that slot, or the doctor is already booked then.

### `GET /patients/:patientId/appointments` — self / linked caregiver / staff
One patient's own appointments, for the patient app. `GET /appointments?patient_id=` stays
staff-only; this is the same data reached through the patient-scoped access check
(`assertCanAccessPatient`) instead of a role gate.
```
?from=YYYY-MM-DD   only this date onward, sorted soonest-first — the "upcoming" view
(omitted)          every appointment, newest first — list / history views
?limit=20          1..100, default 20
```
```ts
{ appointments: Array<{ /* same row shape as GET /appointments */ }> }
```
One endpoint deliberately covers the app's home card, list screen and history — the only
difference is the filter, and the row shape is identical, so a separate `/upcoming` route would
just duplicate the assembly code.

### `POST /patients/:patientId/appointments` — self patient / answer-permitted caregiver
Self-booking. Deliberately a separate schema from the staff endpoint above, not the same route
branching on role — every relaxation the staff form allows (unset doctor, unset time, past
dates, walk_in/urgent, choosing status) makes no sense for a patient booking their own future
visit, so none of them apply here.
```ts
// request
{
  doctor_id: string;                    // required — no "assign later"
  visit_date: string;                   // must be today or later (Thai calendar)
  visit_time: string;                   // "HH:MM", must land on a slot boundary
  visit_type: "routine" | "follow_up";  // urgent/walk_in excluded on purpose
}
// 201 response
{ appointment: <same shape as GET /appointments row above> }
```
`status` is always `scheduled`. Same 409s as the staff endpoint, plus 403 if the requester isn't
the patient themselves (or a caregiver with `can_answer`).

### `PATCH /appointments/:appointmentId/status` — role: nurse/doctor/admin
```ts
{ status: "scheduled" | "checked_in" | "completed" | "missed" | "cancelled" }
{ appointment: <same shape as GET /appointments row above> }
```
No DELETE, by design — `clinic_assessments`/`doctor_notes` reference `appointment_id`; a deleted
row would orphan them, and "this visit never happened" is exactly what `cancelled` already means.

`EventLogRow`:

ยิง red flag อัตโนมัติเมื่อรุนแรงพอ (เข้าคิว "รายการเฝ้าระวัง" เดียวกับธงที่มาจากคำตอบใน

| เงื่อนไข | red_flags.severity |

### `GET /rounds/:id/questions` — self / caregiver / staff
Returns only the questions **currently visible** given what's been answered so far in this

```ts
{
```

```ts
interface QuestionBankRow {
  question_code: string; qid: string | null; item_no: number | null;
  domain_code: string; domain_name_th: string | null;
  question_full_th: string; question_short_th: string | null;
  answer_type: string;   // e.g. "single_choice", "ordinal_scale_0_4", "text", "number"
  options_json: Array<{ code?: string; value?: string; label: string; score: number | null }>;
  respondent: "patient_only" | "caregiver_preferred" | "both";
```

### `PUT /rounds/:id/responses/:questionCode` — self patient / answer-permitted caregiver
```ts
// request
{
  answer_value?: { choice?: string; [key: string]: unknown };  // required unless skipped=true
  skipped?: boolean;
  submitted_at?: string;   // ISO datetime — client's local clock, for offline sync
}
// 200 response
{ response: ResponseRow }
```
- `score` in the response is **always recomputed server-side** from `question_bank.options_json` — don't send it, it's ignored.
- For `answer_type: "single_choice_with_count"` (today: only `MOTOR_FALL_NEAR_FALL`, MOT-05),
  send `answer_value.count` — a positive integer, how many times it happened that day. Optional
  for backward compat, but `MOTOR_FALL_NEAR_FALL`'s red flag ("เกือบล้มซ้ำ") needs it: `near_fall`
  only fires once `count >= 2`; omitting it is treated as `count = 1` (won't fire). 400 if sent
  but not a positive integer. Ignored entirely for every other `answer_type`.
- For `answer_type: "single_choice_with_text"` (today: only `MOOD_IMPULSE_CONTROL`, MOOD-03),
  send `answer_value.text` — what the patient specified, since that option reads
  "มี (ระบุว่าเป็นเรื่องอะไร)" and the detail *is* the clinical content (gambling vs binge eating vs
  hypersexuality are different problems). Optional — a patient may answer "yes" and decline to
  elaborate. Whitespace is trimmed; a blank string is stored as absent. 400 if sent but not a
  string. Ignored entirely for every other `answer_type`.
- 409 if the round isn't `pending` or its window has closed.
- 400 if the question doesn't exist, is inactive, or `respondent = patient_only` and the caller is a caregiver.
```ts
interface ResponseRow {
  id: string; patient_id: string; round_instance_id: string;
  question_code: string; question_version: number;
  answer_value: { choice?: string; score?: number | null; count?: number; text?: string; [key: string]: unknown };
  skipped: boolean; answered_by_role: "patient" | "caregiver"; answered_at: string;
}
```

### `GET /patients/:patientId/rounds` — self / caregiver / staff
Query: `?status=pending` (optional filter: `pending|completed|missed|expired`)
```ts
{ rounds: RoundInstanceRow[] }
```

### Push payload — `data` on a medication reminder

Reminders are sent through Expo. Besides `title`/`body`, a medication reminder carries a `data`
object so the app can open the right dose without querying its way back through three tables:

```ts
{
  type: "medication_reminder";
  prescription_id: string;
  medication_id: string;
  drug_name: string | null;        // null only if the drug has since been removed from the catalogue
  drug_thai_name: string | null;
  dose: string | null;             // exactly as prescribed, unit included -- "1 เม็ด", "ครึ่งเม็ด"
  planned_at: string;              // ISO -- which dose this is, not when the push was sent
}
```

`title` now names the drug (`"ถึงเวลากินยา ลีโวโดปา/คาร์บิโดปา"`) and `body` leads with the dose.
Every reminder used to read identically, so a patient on four drugs across eight daily doses could
not tell which notification was which, and a missed one gave no clue what had been missed. Thai
name wins over generic when present. A drug missing from the catalogue still sends the old generic
text rather than failing — a patient must not miss a dose because our data is incomplete.

### `GET /dashboard/roster`

Every patient with their summary and warning counts in one request. Lives outside
`/patients/:patientId` because it is clinic-scoped, not patient-scoped.

```
?days=7    1..90, default 7 — window for the symptom counters
?limit=50  1..200, default 50
```
```ts
{
  window: { from: string; to: string };
  total_patients: number;   // everyone in the system, not just this page
  roster: Array<{
    patient: PatientFull;
    summary: Summary;         // same shape as GET .../dashboard/summary
    warnings: WarningFlags;   // same shape as GET .../dashboard/warnings
    unreviewed_flag_count: number;   // red flags nobody has acted on, last 30 days
    unreviewed_urgent_count: number;
    caregiver_name: string | null;   // primary active caregiver's display name, if linked
  }>
}
```

`limit` defaults to **50** — and that default lives in the repository, not in this schema, so a
client that omits it silently gets a truncated clinic. Compare `roster.length` against
`total_patients` and say so on screen if they differ: a dashboard that reports "50 patients" for a
clinic of 120 is worse than one that refuses to answer.

The counts are deliberately just counts — no `clinic_tag`, no question, no answer. The screen
that consumes this lists dozens of patients and tends to stay open in a clinic where people walk
past; the most common flag is `suicidal_ideation`. Per-flag detail lives on
`GET /patients/:id/red-flags`, which a clinician opens for one patient during a consult.

Backed by a fixed number of queries regardless of patient count, and every number is computed by
the same pure functions the per-patient endpoints use, so the roster can never disagree with the
individual record. `tests/roster.test.ts` covers the grouping.

## App users (staff only — nurse/doctor/admin)

### `GET /users/app-users`

Who is actually using the mobile app, which is a different question from who is a patient here:
it includes caregivers, who are not patients, and people who registered but never opened the app.

```ts
{
  window_days: 7;
  users: Array<{
    id: string;
    first_name: string; last_name: string;
    role: "patient" | "caregiver";
    phone_number: string | null;
    platform: "ios" | "android" | "web" | null;   // null = no device = never opened the app
    app_version: string | null;
    push_enabled: boolean | null;
    last_response_at: string | null;              // null for every caregiver, see below
    responses_7d: number | null;                  // null for every caregiver
  }>
}
```

`last_response_at` and `responses_7d` are always `null` for caregivers, and that is a data-model
limit rather than missing data: `responses` records `answered_by_role` as `patient` or
`caregiver`, but not *which* user submitted, so a caregiver's own entries cannot be told apart
from another caregiver's on the same patient. A screen showing this must not render that as
"never recorded", or staff will chase the wrong person.

Two things this endpoint deliberately does not answer:

- **Last app open.** `users.last_login_at` is only written by the legacy `POST /auth/login`, which
  patients no longer use — they authenticate against Supabase directly and never reach this API,
  so the column stays null for them. Diary activity is reported instead, which is both recorded
  and more useful: someone who opens the app daily but never records anything still needs a call.
- **OS version.** `devices.platform` is an enum of `ios` / `android` / `web`; there is no column
  for the version behind it.

## Caregiver lookup (any authenticated user)

### `GET /users/lookup?phone=`

Turns a phone number into a caregiver's `id`, because linking a caregiver
(`POST /patients/:id/caregivers`) needs a UUID and the only thing a patient actually knows is
their relative's phone number. `phone` accepts what a person types (`081-234-5678`) and is
normalised to `+66…` with the same rule used at registration, so both sides always agree.

```ts
{ caregiver: { id: string; first_name: string; last_name: string; role: "caregiver" } }
```
404 when no active caregiver account uses that number.

This is a phone → identity lookup, so it is fenced three ways: only `role = caregiver` accounts
that are still active are findable (patients and staff never resolve), only a full exact number
matches (no prefix search, so numbers cannot be swept), and it is rate limited per calling
account — not per IP, since a clinic puts every patient behind one address. The name *is*
returned on purpose: the patient has to confirm they picked the right person before linking,
and a caregiver linked by mistake can read the whole symptom history.

## Notifications (own notifications only)

Rows written by the scheduler for every reminder it sends. Filtered by `user_id` from the token —
never a caller-supplied id — so a caregiver sees what was sent *to them*, not everything about
the patients they are linked to.

### `GET /notifications`
```
?unread_only=true   just the ones not yet opened — the bell badge
?limit=50           1..100, default 50
```
```ts
{ notifications: Array<{
    id: string; type: string; trigger_type: string | null;
    patient_id: string;
    round_instance_id: string | null; prescription_id: string | null;
    medication_log_id: string | null; appointment_id: string | null;
    questions_remaining: number | null;
    triggered_at: string; sent_at: string | null;
    delivery_status: "queued" | "sent" | "failed";
    is_read: boolean;
  }> }
```
The table is a *delivery* log — one row per device the push went to (schema §5) — so a user with
a phone and a tablet, or a stale device row from a reinstall, has several rows for one reminder.
The endpoint collapses those into one entry per event and reports `is_read` as true if any of
them was read, so opening a notification on one device does not leave it unread on the other.
That means the response can be shorter than `limit`; it is not a cursor.

### `PATCH /notifications/:id/read`
```ts
→ { notification: NotificationRow }
```
404 if the id belongs to someone else — the same answer as a nonexistent id, so it cannot be used
to probe which notification ids exist.

Neither route writes to `audit_logs`: reads are excluded by schema §7 (the table would grow too
fast), and marking your own notification read is not a change to patient data.

## Red flags (staff only — nurse/doctor/admin)

Rows written by the backend when an answer trips a §9.4/§9.5 rule at `red`/`urgent` severity.
`warning` severity is query-only by design and never lands here — read those off
`dashboard/warnings` instead.

Patients and caregivers get **403**, including on their own record. The most frequent flag is
`suicidal_ideation`; showing a patient that the system has marked them at risk is a clinical
hazard, not transparency. What the patient should see is the crisis hotline, which belongs to
the mobile app, not this endpoint.

### `GET /patients/:patientId/red-flags`
```
?days=30        1..365, default 30 — longer than dashboard/warnings' 7 on purpose:
                an unreviewed flag must not scroll off the screen by itself
?reviewed=false only flags nobody has looked at yet (omit for all)
```
```ts
{
  window: { from: string; to: string };
  flags: Array<{
    id: string;
    severity: "red" | "urgent";
    clinic_tag: string;          // suicidal_ideation | fall_injury | ...
    question_code: string | null;
    question_th: string | null;  // null when the flag came from an event log
    answer_th: string | null;    // resolved to the label the patient saw, plus what they specified
    answered_at: string | null;
    reviewed: boolean;
    created_at: string;
  }>
}
```

`answer_th` appends whatever the patient specified alongside the choice, separated by ` · ` —
`"เกือบล้มแต่ทรงตัวได้ทัน (ระบุจำนวนครั้ง) · 3 ครั้ง"`, `"มี (ระบุว่าเป็นเรื่องอะไร) · เล่นการพนัน"`.
That detail is the reason the flag exists (MOT-05 only fires at `count >= 2`) or the whole clinical
content of the answer (MOOD-03: gambling and binge eating are different problems), so showing the
bare option label would hide the part a clinician acts on. Answers recorded before this existed
have no `count`/`text` and render exactly as before. The same resolution is used by
`dashboard/app-answers`.

### `PATCH /red-flags/:flagId/review`
```ts
{ reviewed?: boolean }   // default true; false undoes a mis-click
→ { flag: RedFlagRow }
```

Top-level rather than nested under the patient: the flag already has its own id, and requiring a
`patient_id` too would let a caller send one that does not match the flag's real owner.

`reviewed_at` is stamped by Postgres, not by the app. `created_at` comes from the database clock,
so an app-clock `reviewed_at` can land *before* the flag existed whenever the two clocks differ —
a screen that says a nurse acknowledged an alert before it was raised destroys trust in every
timestamp on the page.

Writes to `audit_logs` (`UPDATE` / `red_flags`). Who silenced a safety alert and when has to stay
answerable.

`answer_th` is resolved server-side from `question_bank.options_json` rather than returning the
raw code, because the code alone cannot be acted on: `sometimes` and `plan` both raise
`suicidal_ideation` but mean very different things at the bedside. A skipped answer reads
`"ผู้ป่วยข้ามคำถามนี้"` — MOOD-04 treats a skip as fail-safe and flags it, so the reader has to
be able to tell a skip from an answer.

## Audit log (admin only)

`audit_logs` has been written to since the very first CREATE/UPDATE endpoints — 22 routes wire
the `auditLog` middleware — but until now nothing could read it back. Restricted to `admin`,
not the usual `nurse`/`doctor`/`admin` staff set: this is a system-wide "who changed what" trail,
a different sensitivity tier than a single patient's record.

### `GET /audit-logs`
```
?target_table=   e.g. "appointments", "patient_medications" — omit for all tables
?user_id=        only this account's actions
?action=         CREATE | UPDATE | DELETE (READ is a valid enum value but no route ever logs
                 reads — see middlewares/auditLog.ts — so it will never actually match a row)
?before=         ISO datetime — page backward, same idea as /appointments?before=
?limit=          1..200, default 50
```
```ts
{
  logs: Array<{
    id: string;
    action: "READ" | "CREATE" | "UPDATE" | "DELETE";
    status: "success" | "failed";        // failed = the request itself errored, still logged
    target_table: string;
    target_id: string | null;
    old_value: unknown;
    new_value: unknown;
    created_at: string;
    actor: { id: string; name: string } | null;  // null: system action, or the account was deleted since
  }>
}
```

Doesn't write its own `audit_logs` row — logging a read of the audit log would recurse into the
same growth problem the schema notes already warn about. `services/auditLogService.ts` separates
`assembleAuditLogs` (pure, tested without a DB) from the fetch, the same split
`appointmentService.assembleAppointments` uses, for the same reason: cross-user data mixups in
who-did-what are the one class of bug in this file worth catching without a live database.

## Question bank (any logged-in account, read-only)

### `GET /question-bank`

Every question in the catalog plus the 7 check-in rounds (`checkin_templates`), no `requireRole`
— same reasoning as `/medications`: this isn't patient data, so it doesn't need the staff-only
gate that most of this file's endpoints have. Read-only on purpose: the xlsx workbook
(`docs/PDLIFE_Question_Bank_master_v1.xlsx`) is the one source of truth, regenerated into
`seed/seed.sql` by `seed/gen_seed.py` — a web editor here would create a second source that
silently loses edits the next time someone re-runs the generator.

```ts
{
  questions: Array<{
    question_code: string;
    qid: string | null;
    item_no: number | null;
    domain_code: string;
    domain_name_th: string | null;
    question_full_th: string;
    answer_type: string;
    options_json: Array<{ code?: string; value?: string; label: string; score: number | null }>;
    respondent: "patient_only" | "caregiver_preferred" | "both";
    mvp_phase: "MVP1" | "MVP2" | null;
    active: boolean;
    rule_status: "no_rule" | "warning_only" | "enforced" | "safety_gate" | "not_enforced";
    template_codes: string[];   // which of the 7 rounds ask this question
  }>;
  templates: Array<{
    template_code: string;
    template_name_th: string;
    purpose: string | null;
    trigger_type: string;
    window_minutes: number | null;
    max_questions_target: number | null;
    notification_copy_th: string | null;
    mvp_phase: "MVP1" | "MVP2" | null;
    active: boolean;
  }>;
}
```

`rule_status` is the point of this endpoint beyond being a static catalog dump: it surfaces,
per question, whether a `red`/`urgent` red-flag rule actually fires. `STRUCTURED_RULE_OVERRIDES`
(`config/constants.ts`) made 11 of 12 such questions fire for real today — before this endpoint
existed, the only way to know which ones were covered was to read that file. `not_enforced`
means a `red`/`urgent` question whose `red_flag_json.rule` is still free text and isn't in the
override table — it will not write a row to `red_flags` no matter what a patient answers.
`safety_gate` is `MOOD_SUICIDAL_IDEATION` specifically, which never goes through
`checkStructuredRedFlagRule` at all (see `checkMoodSafetyGate`).
