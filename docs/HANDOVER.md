## 3. ตั้งเครื่องใหม่

```powershell
git clone https://github.com/HASIM6287/pdlife-backend.git
git clone https://github.com/HASIM6287/pdlife-web.git

cd pdlife-backend ; npm install
cd ..\pdlife-web  ; npm install
```

สร้างไฟล์ env เอง (ไม่อยู่ใน git โดยตั้งใจ)

| ไฟล์ | ดูตัวอย่างจาก |
|---|---|
| `pdlife-backend\.env` | `.env.test` (ค่าปลอมทั้งหมด ดูชื่อตัวแปรได้) |
| `pdlife-web\.env.local` | `.env.example` |

เปิดทั้งสองตัวด้วยคำสั่งเดียวจากโฟลเดอร์แม่

```powershell
.\dev          # เปิด backend :3000 และ web :3001
.\dev -Clean   # ล้างแคช .next ก่อนเปิด — ใช้เมื่อเจอ 404 หรือ error แปลก ๆ
.\dev -Stop    # ปิดทั้งคู่
```

**ถ้าแก้ไฟล์เยอะหรือเปลี่ยนชื่อไฟล์ระหว่าง dev server รันอยู่ ให้ `.\dev -Clean` เสมอ** —
Next เก็บ chunk เก่าปนใหม่แล้วจะได้ error ที่ไล่หาต้นเหตุไม่เจอ (เคยเสียเวลากับเรื่องนี้มาแล้ว)

## 4. 🔴 Migration ที่ต้องรันด้วยมือ

รันตามลำดับใน **Supabase SQL Editor** ของโปรเจกต์ทดสอบ

| ไฟล์ | ทำอะไร | สถานะ |
|---|---|---|
| `0001_init_schema.sql` | สร้าง schema ทั้งหมด | รันแล้ว |
| `0002_grant_service_role.sql` | ให้สิทธิ์ service_role บน schema `pdlife` | รันแล้ว |
| `0003_one_assessment_per_appointment.sql` | หนึ่งการมาตรวจ = หนึ่งฟอร์มคัดกรอง | **ตรวจก่อนว่ารันหรือยัง** |
| `0004_one_doctor_note_per_appointment.sql` | หนึ่งการมาตรวจ = หนึ่งบันทึกแพทย์ + index ที่ขาด | **ตรวจก่อนว่ารันหรือยัง** |

ตรวจว่ารันไปแล้วหรือยัง
```sql
SELECT tablename, indexname, indexdef FROM pg_indexes
WHERE tablename IN ('clinic_assessments', 'doctor_notes');
```
เห็นคำว่า `UNIQUE` ทั้งสองตาราง = ครบแล้ว

**การ commit ไฟล์ SQL ไม่ได้รันมัน** — ระบบยังทำงานได้ถ้ายังไม่รัน แค่ขาดตาข่ายกันคนสองคน
กดบันทึกพร้อมกัน

## 5. สถานะงาน

### ✅ ใช้งานได้จริงแล้ว — บันทึกลงฐานข้อมูล

```
เพิ่มนัด / Walk-in  →  เช็คอิน  →  พยาบาลคัดกรอง  →  แพทย์อ่าน  →  แพทย์บันทึก
```

| endpoint | |
|---|---|
| `GET /api/appointments` | `?date=` วันเดียว · `?before=` ย้อนหลัง · `?patient_id=` รายคน |
| `POST /api/appointments` | สร้างนัด รวม walk-in — กันคิวชนกันของหมอแล้ว (409 ถ้าซ้ำ) ดูข้อ 3 ด้านล่าง |
| `PATCH /api/appointments/:id/status` | เช็คอิน · ยกเลิก · เอากลับ |
| `GET/PUT /api/appointments/:id/assessment` | ฟอร์มคัดกรอง 26 ข้อ |
| `PATCH /api/appointments/:id/assessment/opened` | แพทย์เปิดอ่านฟอร์ม |
| `GET/PUT /api/appointments/:id/note` | บันทึกผลการตรวจ |
| `GET /api/users/staff?role=doctor` | รายชื่อแพทย์ |
| `GET /api/dashboard/roster` | ทะเบียนทั้งคลินิกในคำขอเดียว |
| `GET /api/users/app-users` | ใครใช้แอปอยู่จริง |
| `GET /api/patients/:id/dashboard/app-answers` | คำตอบล่าสุดของผู้ป่วยในแอป แปลงให้ตรงกับ 26 ข้อของฟอร์มคัดกรอง — ใช้ทำตารางเทียบ "แอป vs พยาบาล" |
| `GET /api/audit-logs` | ประวัติการเปลี่ยนแปลงข้อมูลทั้งระบบ — **admin เท่านั้น** (เขียนมาตั้งแต่ต้นแล้ว แต่ไม่เคยมีทางอ่านมาก่อน) มีหน้าจอที่ `/staff/audit-log` ในเว็บแล้ว |
| `GET /api/question-bank` | คลังคำถามทั้งหมด + 7 รอบเช็คอิน อ่านอย่างเดียว (staff ทุกคน) — โชว์ `rule_status` ต่อข้อว่า red flag ยิงจริงหรือยัง มีหน้าจอที่ `/staff/question-bank` ในเว็บแล้ว |
| `POST/GET /api/patients/:id/event-logs` | เหตุการณ์ฉุกเฉินนอกรอบคำถาม (สำลัก/dyskinesia รุนแรง/ยาไม่ออกฤทธิ์/อื่นๆ) — ผู้ป่วยเอง/ผู้ดูแลที่มีสิทธิ์ตอบแทนเท่านั้นที่บันทึกได้ ยิง red flag อัตโนมัติเมื่อรุนแรงพอ (เข้าคิว "รายการเฝ้าระวัง" เดียวกัน) มีหน้าจอแสดงที่แท็บภาพรวมของเวชระเบียนแล้ว — **ตารางนี้เพิ่งต่อสายวันนี้ ก่อนหน้านี้มีอยู่ใน schema (§6.3) แต่ไม่มีทางเขียนเลยสักทาง เลยไม่มีข้อมูลจริงจนกว่าแอปจะเริ่มยิง endpoint นี้** |
| `GET /api/appointments/available-slots` | slot ว่าง/ไม่ว่างของหมอคนหนึ่งวันหนึ่ง — ไม่กัน role |
| `POST /api/patients/:id/appointments` | ผู้ป่วย/ผู้ดูแลจองนัดเอง — ทีมแอปยืนยันแล้วว่าจะปรับ UI ให้ตรงกับ contract นี้เอง (ดูข้อ 3 ด้านล่าง) |
| `POST /api/patients/:id/prescriptions` · `PATCH /api/prescriptions/:id` | จ่ายยา/ปรับยา/หยุดยา — **role: doctor/nurse/admin** (admin เพิ่มมาตามคำขอ ดูหัวข้อ "admin สั่งยาได้เหมือน doctor/nurse" ด้านล่าง) เว็บมีฟอร์มจริงแล้วที่หน้าบันทึกแพทย์ (ตรง "ปรับยาหรือไม่" หรือปุ่ม "+ จ่ายยา" แยกสำหรับคนไข้ที่ไม่เคยมีใบสั่งยาเลย) — เดิมมี endpoint มานานแล้วแต่ไม่มีหน้าจอเรียกใช้เลยสักที่ |

*(ยังมี endpoint ของแอปผู้ป่วยอีกชุด — ดู `API_CONTRACT.md`)*

## 6. การตัดสินใจที่ต้องรู้ (อ่านจากโค้ดเองไม่ได้)

### นัดหมายไม่ใช่แค่รายการปฏิทิน
`schedulerService.generateDailyAndWeeklyRounds` สร้างรอบถามอาการ**เฉพาะผู้ป่วยที่มีนัดภายใน
7 วัน** — แถวใน `appointments` คือสวิตช์ที่เปิดให้แอปเริ่มถามอาการคนนั้น
**ไม่มีนัด = แอปไม่ถามอะไรเลย**

### ไม่มีการลบนัด และจะไม่มี
ใช้ `status = cancelled` แทนเสมอ นัดที่หายไปทำให้ตอบไม่ได้ว่าเคยมีคนนัดไหม และ
`clinic_assessments` / `doctor_notes` อ้าง `appointment_id` อยู่ — ฐานข้อมูลก็ปฏิเสธการลบ
นัดที่มีฟอร์มผูกอยู่ (FK ไม่มี `ON DELETE CASCADE` โดยตั้งใจ)

การยกเลิกย้อนกลับได้เสมอ (ปุ่ม "เอากลับ") เพราะกดผิดแล้วติดตายทำให้คนไปสร้างนัดใบใหม่แทน

### ฟอร์มเป็นของ "การมาตรวจครั้งนั้น" ไม่ใช่ของผู้ป่วย
`clinic_assessments.appointment_id` และ `doctor_notes.appointment_id` เป็น `NOT NULL`
คนเดียวกันมา 5 ครั้ง = 5 ใบแยกกัน เหมือนฟอร์มกระดาษ
**อย่าย้าย endpoint พวกนี้ไปอยู่ใต้ `/patients/:id`** จะเปิดช่องให้เข้าใจผิดว่ามีใบเดียวต่อคน

### นัดที่ยกเลิกยังต้องเห็นในรายการ "บันทึกที่ผ่านมา"
รายการงานประจำวันกรองนัดที่ยกเลิกทิ้ง แต่หน้าประวัติ**ต้องไม่กรอง** — ฟอร์มที่เผลอกรอกลง
นัดที่ยกเลิกยังอยู่ในฐานข้อมูล ถ้าไม่มีที่ให้เปิดดูก็เท่ากับข้อมูลนั้นหายไป

### แก้ฟอร์มที่แพทย์อ่านไปแล้วได้ แต่ต้องเตือน
ไม่ห้าม เพราะพยาบาลติ๊กผิดเป็นเรื่องปกติ และถ้าห้ามเขาจะไปเขียนแก้ใน `other_note`
ซึ่งอ่านยากกว่าและไม่มีใครเห็น — ใช้การเตือน + `audit_logs` แทนการล็อก

### `screened_by` กับ `nurse_id` ไม่ได้ซ้ำกัน
`nurse_id` = บัญชีที่กดบันทึก แก้ไม่ได้ · `screened_by` = ชื่อคนคัดกรอง เติมให้แต่แก้ได้
เพราะคลินิกมักมีเครื่องกลางเปิดค้างแล้วพยาบาลหลายคนสลับกันใช้

### `submitted_at` ประทับใหม่ทุกครั้งที่กดส่ง
ตาราง**ไม่มี `updated_at`** แพทย์จึงไม่มีทางรู้ว่าฟอร์มถูกแก้หลังตัวเองอ่านไปแล้วหรือเปล่า
การให้ `submitted_at` เป็น "ส่งครั้งล่าสุด" ทำให้เทียบกับ `doctor_opened_at` ได้
**ถ้าวันหนึ่งเพิ่มคอลัมน์ `updated_at` ให้กลับมาแก้ตรงนี้**

### บันทึกผลตรวจแล้วนัดกลายเป็น "เสร็จแล้ว" อัตโนมัติ
ไม่แตะนัดที่ยกเลิกหรือไม่มาตามนัด — สองอย่างนั้นเป็นข้อเท็จจริงที่เกิดไปแล้ว

### วันนัดถัดไปไม่สร้างนัดให้อัตโนมัติ
บันทึกมีแค่*วันที่* ไม่มีเวลา ไม่มีแพทย์ ไม่มีประเภทนัด — ขึ้นปุ่มให้กดยืนยันเองแทน
และการแก้บันทึกทีหลังจะไม่ทำให้เกิดนัดซ้ำ

### admin สั่งยาได้เหมือน doctor/nurse — ตัดสินใจตั้งใจ ไม่ใช่ช่องโหว่
`POST /patients/:id/prescriptions` และ `PATCH /prescriptions/:id` เดิมจำกัดแค่ doctor/nurse
เพราะเป็นคำสั่งทางคลินิก แต่ผู้ใช้ยืนยันแล้ว (2026-09) ว่าต้องการให้ admin สั่ง/ปรับยาได้จริง
ในระบบจริง ไม่ใช่แค่ทางลัดตอนทดสอบ — ถามย้ำก่อนแก้เพราะเป็นการลบเส้นแบ่งสิทธิ์ทางคลินิกที่
ตั้งใจไว้แต่แรก ผู้ใช้เลือกยืนยันแบบถาวรหลังเห็น tradeoff แล้ว (audit log จะโชว์ "admin สั่งยา"
ได้ตั้งแต่นี้ไป ซึ่งเป็นเรื่องปกติแล้วตามที่ตกลงกัน) แก้ที่ 3 จุด: route guard สองที่
(`patientRoutes.ts` POST, `prescriptionRoutes.ts` PATCH) + เช็คซ้ำในเซอร์วิส
(`prescriptionService.createPrescription`)

### แจ้งเตือนกินยาบอกชื่อยาและขนาดแล้ว (ก.ย. 2569)

เดิม `generateMedicationReminders` ส่ง "ถึงเวลากินยา" เหมือนกันหมดทุกตัวยา — ผู้ป่วยที่กินยา 4 ตัว
8 มื้อต่อวันจึงแยกไม่ออกว่าอันไหนของยาตัวไหน และถ้าพลาดไปหนึ่งอันก็ไม่รู้ว่าพลาดอะไร

ตอนนี้ดึงชื่อยาจาก catalog แบบ batch ครั้งเดียวต่อ tick (`findMedicationsByIds` — **ห้ามยิงทีละโดส**
จำนวนคำขอจะโตตามจำนวนคนไข้ ซึ่งขัดกับเหตุผลของ `REMINDER_DISPATCH_CONCURRENCY` ข้างล่าง) แล้ว
ประกอบข้อความด้วย `composeMedicationReminder` กับหาขนาดยาด้วย `doseForTime` — สองตัวนี้เป็น pure
function ที่ export ไว้ให้เทสได้โดยไม่ต่อ DB (`tests/medicationReminder.test.ts`)

`doseForTime` ต้องเผื่อคีย์เวลาสองรูปแบบ เพราะคอลัมน์ `TIME[]` ของ Postgres คืนค่าเป็น `HH:MM:SS`
เสมอ แต่ `doses` เป็น JSON ที่ฝั่งเว็บตั้งคีย์เอง จึงมีทั้ง `08:00` และ `08:00:00` ปนกันตามยุคที่
บันทึก — กับดักเดิมที่โปรเจกต์นี้เคยโดนมาแล้วสองรอบ (visit_time, scheduled_times)

`notify()` รับ `data` เพิ่ม (optional) ส่งต่อเข้า Expo push ให้แอปเปิดหน้าที่ถูกต้องได้เลยโดยไม่ต้อง
ไล่ query 3 ตารางจากเครื่องผู้ใช้ — **ทีมแอปต้องรับฟิลด์นี้ฝั่งเขาเอง** (รูปแบบอยู่ใน
`API_CONTRACT.md` หัวข้อ "Push payload")

### scheduler tick ยิงแจ้งเตือนพร้อมกันแบบจำกัดจำนวน ไม่ใช่ทีละคน
`generateMedicationReminders` เดิมวน `for...of` + `await notify()` ทีละคนไข้ — cron job รันทุก
1 นาที (`src/jobs/scheduler.ts`) ถ้าคนไข้เยอะและเวลากินยาชนกัน (เช่นมื้อเช้าพร้อมกันหมด) tick
เดียวอาจกินเวลานานกว่ารอบถัดไปที่จะมาถึง ทำให้แจ้งเตือนกินยาช้าลงเรื่อยๆ ตามจำนวนคนไข้ — ไม่ทำ
ให้ระบบพัง (มี guard กันไม่ให้ tick ใหม่ทับ tick เก่า) แต่ push จะมาช้ากว่าที่ควร

แก้ด้วย `mapWithConcurrency` (`src/utils/concurrency.ts`, pure utility ทั่วไป เทสแยกได้) ยิง
พร้อมกันสูงสุด `REMINDER_DISPATCH_CONCURRENCY = 25` ตัวต่อครั้ง — เลขนี้เดาแบบสมเหตุสมผล
**ยังไม่เคยวัด load จริง** ปรับได้ถ้าเจอปัญหาจริงตอนใช้งาน

**แก้ครบทั้ง 6 จุดที่มี pattern นี้แล้ว** — `generatePostMedRounds` (ขนานระดับ medication log),
`generatePreNextMedRounds` (ขนานระดับใบสั่งยา — inner loop ต่อโดสยังเรียงกันเหมือนเดิมเพราะ
น้อยอยู่แล้ว ตัวคูณจริงคือจำนวนคนไข้), `generateDailyAndWeeklyRounds` (ขนานระดับคนไข้ — สามรอบ
เช้า/เย็น/รายสัปดาห์ของคนเดียวกันยังรันเรียงกัน + ขนานระดับนัดสำหรับ previsit) ใช้
`mapWithConcurrency` ตัวเดียวกันทุกจุด ไม่มีจุดไหนเหลือ for-loop ทีละคนแบบเดิมแล้ว —
`sweepStaleMedicationLogs` **ไม่ได้แตะ** เพราะไม่เรียก `notify()` (ไม่มี HTTP ออกนอกระบบ แค่
เขียน DB) ความเสี่ยงคนละระดับ ยังไม่เข้าเกณฑ์ที่ต้องรีบแก้

ตั้งใจไม่ทำ **การรวม batch ข้ามคนไข้เป็น Expo push request เดียว** (Expo รับได้ทีละ 100 ข้อความ
ต่อคำขอ) แม้จะลด HTTP request ได้อีก เพราะต้องรื้อ `notify()` ที่ผูก 1 event = 1 แถวใน
`notifications` ให้รองรับหลาย patient ต่อคำขอ — ซับซ้อนเกินความจำเป็นตอนนี้ เพราะแค่ยิงพร้อมกัน
แบบจำกัดจำนวนก็พอสำหรับ scale ปัจจุบันแล้ว (คำนวณคร่าวๆ คนไข้หลักพันเสร็จได้ในไม่กี่สิบวินาที)

### เกณฑ์ที่ซ้ำสองฝั่งมีเทสจับไว้
`30 นาที = กินสาย` และ `30 วัน = ช่วงดูสัญญาณเตือน` เขียนอยู่ทั้งเว็บและ backend
`tests/thresholdSync.test.ts` อ่านไฟล์ของเว็บมาเทียบ **ถ้าย้ายไฟล์ constants ของเว็บ
ให้แก้ path ในเทส อย่าลบเทสทิ้ง**

ทางแก้ที่ถูกต้องคือให้ API ส่งเกณฑ์มาด้วย — ทำตอนออกแบบ API รอบหน้า

## 7. วิธีทำงานที่ตกลงกันไว้

- **วางแผนก่อนลงมือเสมอ** ให้เห็นชอบก่อนค่อยเขียนโค้ด
- **แก้ schema เป็นทางเลือกสุดท้าย** และต้องบอกก่อนทุกครั้ง
- **คอมเมนต์ในโค้ดเขียนภาษาไทย** และอธิบาย*ทำไม* ไม่ใช่*อะไร*
- **ต่อ API ก่อน แล้วค่อยลบ mock ของส่วนนั้น** ไม่ใช่ลบก่อน
- **ห้ามแสดงตัวเลขทางคลินิกที่มาจากข้อมูลจำลอง** ปิดไว้พร้อมเขียนบอกดีกว่า
- git: ทำงานบน `develop` → PR → merge บน GitHub → `git pull` กลับ
  **อย่า `git merge` ในเครื่องเอง** (ตั้ง `pull.ff only` ไว้แล้วทั้งสองรีโป)
